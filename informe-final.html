1. Introduccion

La empresa salvadorena “Dulce Hogar”, dedicada a la reposteria artesanal, necesita publicar su catalogo en linea y recibir pedidos por Internet. Actualmente vende por WhatsApp y redes sociales. El equipo fue contratado como administrador del servidor web para montar la infraestructura completa sobre Ubuntu Server LTS (ejecutado con WSL2 en equipos Windows).

El presente informe documenta las cuatro fases del laboratorio: dimensionamiento del servidor, instalacion de Apache, configuracion de un Virtual Host con Reverse Proxy hacia la API de la Unidad 1, y publicacion del sitio por HTTPS local con mkcert.

2. Fase 1 — Dimensionamiento colaborativo

2.1 ¿Bastan 2 vCPU y 4 GB de RAM para el trafico normal y para el pico?

El factor pico es 3,000 / 500 = 6x. Para el trafico diario (500 visitas/dia, unas 0.006 visitas/segundo) 2 vCPU y 4 GB son mas que suficientes para servir un catalogo estatico. Para el pico, el volumen sigue siendo moderado si el contenido es estatico y cacheable; el riesgo aparece si las visitas se concentran en pocos minutos o si el backend hace trabajo pesado por peticion.

2.2 ¿Escalado vertical u horizontal?

Para una PyME con picos estacionales recomendamos escalado vertical (mas RAM/CPU) apoyado en cache y, si el pico es muy puntual, en una CDN o “cloud burst”. Es inmediato, no exige redisenar la aplicacion y evita el costo de mantener un segundo servidor permanente, algo sobredimensionado para un trafico que solo sube en dias festivos.

2.3 Recurso a vigilar primero

Primero la RAM: Apache levanta multiples procesos/threads y si se agota la memoria entra el swap y la latencia se dispara. Luego CPU (top, load average), despues disco (iostat, df -h) y red (iftop, ss -s).

2.4 Nube o servidor local

CriterioNube (VPS)Servidor local
Costo inicialBajo (pago mensual, sin CAPEX)Alto (hardware, energia, respaldo)
EscalabilidadAlta (subir de plan en minutos)Limitada por el hardware comprado

Decision del equipo: NUBE (VPS) para produccion por su escalabilidad ante los picos y su menor mantenimiento; el servidor LOCAL (WSL2) como entorno de desarrollo y pruebas.

3. Fase 2 — Instalacion de Apache

Comandos principales:

sudo apt update
sudo apt install -y apache2
sudo systemctl enable --now apache2
curl http://localhost
sudo apache2ctl configtest   # -> Syntax OK

Apache 2.4.58 quedo active (running) y sirvio la pagina por defecto “It works!”. sites-available guarda las definiciones de los sitios; sites-enabled contiene los enlaces a los que Apache carga realmente (gestionados con a2ensite/a2dissite). configtest es clave porque valida la sintaxis antes de reiniciar y evita dejar el servidor caido.

4. Fase 3 — Virtual Host + Reverse Proxy

Se creo /var/www/dulcehogar.local con propietario www-data, se habilitaron los modulos proxy, proxy_http y headers, y se definio el Virtual Host dulcehogar.local.conf que envia /api al backend del puerto 9000.

ProxyPreserveHost On
ProxyPass        /api http://localhost:9000/api
ProxyPassReverse /api http://localhost:9000/api

ProxyPass reescribe la peticion de ida (Apache → backend) y ProxyPassReverse reescribe las cabeceras de redireccion de vuelta para que apuntan al dominio publico y no al backend interno. Prueba de integracion: 

curl http://dulcehogar.local/api/saludo?nombre=Equipo
{"mensaje": "Hola Equipo, bienvenido a Dulce Hogar",
 "servicio": "API Unidad 1", "puerto": 9000}

Esta respuesta demuestra que las Unidades 1 y 2 estan conectadas: el texto lo genera la API (Unidad 1) y lo entrega Apache (Unidad 2) mediante el Reverse Proxy.

5. Fase 4 — HTTPS local con mkcert

mkcert -install            # con guion (crea la CA local y la confia)
mkcert dulcehogar.local    # genera el par certificado/clave
# ports.conf incluye: Listen 8900
sudo a2enmod ssl
sudo a2ensite dulcehogar.local-ssl.conf
sudo systemctl restart apache2

El sitio quedo disponible en https://dulcehogar.local:8900. El certificado de mkcert es valido para dulcehogar.local y expira el 9 de enero de 2029. certbot no sirve para dominios .local porque Let’s Encrypt solo emite para dominios publicos validables por Internet. Un certificado autofirmado provoca advertencia del navegador; el de mkcert no, porque su CA local se instala en el almacen de confianza.

6. Conclusiones

  • Apache sobre Ubuntu LTS es una solucion libre, estable y adecuada para el catalogo de Dulce Hogar.
  • El Reverse Proxy permite separar el front-end estatico (Apache) del back-end (API), uniendo las Unidades 1 y 2.
  • mkcert habilita HTTPS local confiable sin comprar certificados, ideal para desarrollo y pruebas.
  • Para produccion se recomienda migrar a un VPS, usar certbot/Let’s Encrypt y HTTPS en el puerto 443.
